## Context

Текущий `src/index.ts` выводит сообщение в консоль. В `package.json` есть скрипт `build` на базе `tsc`. Конфигурация OpenSpec использует схему `spec-driven`; опубликованных возможностей пока нет.

## Goals / Non-Goals

**Цели:** запуск и сборка Electron-приложения, воспроизводимые проверки и типизированные контракты для последующих изменений.

**Вне объёма:** управление клиентом PoE, чтение экрана и буфера обмена, хранение калибровки, алгоритмы парсинга и крафта, дистрибутивы.

## Decisions

1. **Разделить Electron main, preload и Vue renderer.** Main создаёт окно. Renderer запускается через Vite в разработке и загружается из результата сборки в обычном режиме. Preload оставляет точку для будущего типизированного моста. Включить изоляцию контекста и sandbox renderer, выключить Node.js integration. В первой итерации мосту не требуются прикладные IPC-методы.
2. **Разместить предметную логику в `src/domain/`.** Контракты не импортируют Electron, Vue и системные API. Vitest проверяет их в Node. Внешние значения проверяются Zod-схемами. Типы данных выводятся из схем там, где схемы являются источником структуры.
3. **Развести геометрию инвентаря и Currency Stash.** Инвентарь описывается прямоугольной областью и размерами регулярной сетки. Currency Stash описывается областью и именованными прямоугольными слотами, поскольку контракт должен допускать разное расположение и размер ячеек. Координаты задаются относительно начала тестовой поверхности, по осям вправо и вниз. Слоты задаются относительно области вкладки. Преобразование координат рабочего стола и DPI отложено до отдельного изменения.
4. **Описать операции через явные результаты.** `ItemParser.parse(text)` возвращает модель предмета или типизированную ошибку. Начальная модель содержит базовый тип, редкость и список модификаторов. `CraftingEngine.plan(request)` получает модель предмета, ограничения по валюте и цель, заданную идентификатором, и возвращает упорядоченные намерения применить валюту или типизированную причину, почему план недоступен. Намерения содержат данные о предмете и валюте; исполнителя в этой итерации нет. Тестовые реализации нужны только для проверки стыковки контрактов.
5. **Завести короткий комплект документации.** `docs/README.md` описывает запуск и проверки, `docs/architecture/` хранит решения и причины выбора, `docs/progress/current-state.md` фиксирует выполненные задачи, результаты проверок и остаток работ. Корневой `AGENTS.md` фиксирует согласование до реализации, порядок работы с OpenSpec и условия закрытия задач.

## Risks / Trade-offs

- Разработка и запуск из собранных файлов загружают renderer разными способами. Проверить оба пути вручную.
- Реальная разметка вкладки и варианты текста предметов ещё не проверены. Держать контракты минимальными и использовать синтетические фикстуры.
- Точная версия Node.js и совместимые версии зависимостей будут закреплены при реализации с обновлением npm lockfile. Для запуска и сборки предусмотреть npm-скрипты без привязки к синтаксису конкретной оболочки.
